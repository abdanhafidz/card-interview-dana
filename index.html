Q3

Handling a High-Priority Mid-Sprint Request

Interview Question

The engineering team is halfway through a sprint. A stakeholder suddenly requests a high-priority feature and wants it delivered within the same sprint. How would you handle it?

Recommended Follow-Up Questions

Before answering:

  • How critical is the feature to the business?
  • What is driving the urgency?
  • Is the deadline fixed?
  • What is the estimated engineering effort?
  • What is the current team capacity?
  • Are there dependencies?
  • Can any current sprint items be deprioritized?
  • Is a smaller demo-ready scope acceptable?

Scenario Information

  • Feature is related to a new merchant payment flow.
  • Needed for an external partner demo on Friday.
  • Full implementation requires around 5 person-days.
  • Team:

- 2 backend engineers

- 1 frontend engineer

- 1 QA engineer

  • Team is already fully committed.
  • Around 60% of sprint work is complete.

Your Core Answer

  • Perform impact analysis.
  • Identify low-priority sprint items.
  • Move lower-priority work back to the Product Backlog.
  • Make the urgent feature top priority.
  • Reassign work based on team capacity.
  • Define acceptance criteria.
  • Consider a smaller demo-ready version if full implementation is too large.

Key Feedback

  • Correct term: move postponed work back to the Product Backlog, not Sprint Backlog.
  • Avoid solving the issue by telling engineers to “code faster.”
  • Core PM problem is scope and trade-off management.

Polished Answer

Based on the information, I would first conduct an impact analysis with the engineering team to identify which current sprint items could realistically be postponed without creating major dependencies or business risks.

Since the new feature requires around five person-days and the team is already fully committed, I would not simply add it on top of the existing sprint scope because that could increase delivery risk and reduce quality.

I would identify the lowest-priority items with minimal dependencies and propose moving them back to the Product Backlog. Then I would present the trade-off clearly to the stakeholder: if we prioritize the merchant payment feature for the Friday demo, these specific items would likely move to the next sprint.

After getting stakeholder alignment, I would update the sprint plan, assign the work based on engineering capacity, define clear acceptance criteria for the demo, and monitor blockers closely until Friday.

If the full production-ready feature is still too large for the available capacity, I would discuss whether we could deliver a smaller demo-ready scope first and schedule the remaining production requirements for the next sprint.

Q4

Engineering vs Stakeholder Conflict

Interview Question

A backend engineer says a feature will require at least five days to implement properly, but the business stakeholder insists it must be completed in two days and says, “It’s just a simple API change.” How would you handle the disagreement?

Your Core Answer

  • Do not immediately take either side.
  • Be honest with the stakeholder.
  • Validate whether the engineer’s five-day estimate is justified.
  • Explain the complexity to the stakeholder in simple language.
  • Offer a compromise:

- Prototype

- Mock backend

- Dummy data

  • Let frontend demonstrate the flow.
  • Finish the production-ready implementation after the demo.

Key Feedback

  • Do not imply the engineer might simply be lazy.
  • Ask for a breakdown of the estimate:

- Development

- Testing

- Integration

- Security

- Deployment

  • Do not automatically make the stakeholder’s request the highest priority.
  • In fintech, do not compromise mandatory security or quality requirements.

Polished Answer

First, I would avoid immediately taking either side. I would clarify the business reason behind the two-day deadline and ask the backend engineer to break down the five-day estimate, including development, testing, integration, and potential technical risks.

If the five-day estimate is justified, I would explain the situation to the stakeholder in business-friendly language rather than using too much technical detail. I would make the trade-off clear: forcing the full implementation into two days could create quality, reliability, or security risks.

At the same time, I would not simply tell the stakeholder that the request is impossible. I would propose alternatives that still achieve the business objective.

For example, if the main requirement is to demonstrate the feature in two days, we could build a prototype or use mocked backend responses so the frontend can demonstrate the intended user flow. After the demo, the engineering team could complete the production-ready API implementation with proper testing and integration.

My goal would be to make sure both sides understand the constraints and agree on a solution that protects the deadline without compromising production quality.

Prioritization: Incident vs Feature vs Technical Debt

Interview Question

You have three requests:

Request A: A major merchant reports a payment issue affecting around 5% of transactions.

Request B: Product wants a new feature launched this week because a competitor released something similar.

Request C: Engineering wants to refactor an old service because technical debt is slowing development.

You only have capacity to prioritize one immediately. Which one do you choose?

Your Core Answer

You prioritized Request A because:

  • It affects a real production flow.
  • It has business impact.
  • It can affect governance, reliability, and customer experience.
  • It is more urgent than a feature opportunity or technical debt.

Key Feedback

The strongest reason is not merely “compliance is external.”

The stronger PM framing:

  • Request A = confirmed production impact.
  • Request B = future strategic opportunity.
  • Request C = long-term maintainability concern.

Polished Answer

I would prioritize Request A because it is already affecting real payment transactions for a major merchant. Even though the issue only affects around 5% of transactions, it directly impacts users, merchant trust, transaction success rate, and potentially revenue and regulatory risk.

Request B is important from a competitive and business-growth perspective, but it is still a future opportunity rather than an active production problem. Request C is also important because technical debt can reduce engineering velocity over time, but it is primarily a long-term maintainability issue.

So I would allocate the available capacity to Request A first, while communicating clearly to the Product team and Engineering team why their requests are being temporarily deprioritized.

For Request B, I would explain that we are protecting the reliability of the core payment experience first, then reassess the feature launch as soon as the incident is stabilized. For Request C, I would make sure the refactoring work remains visible in the backlog and is scheduled deliberately rather than being postponed indefinitely.

My prioritization would be based on immediate business impact, customer impact, operational risk, and urgency.

Q7

Risk Management — Unstable External API

Interview Question

Your project is scheduled to launch in two weeks. An engineer tells you that an external API dependency has become unstable and may delay the launch. How would you manage the risk and communicate it to stakeholders?

Your Core Answer

  • Follow up with engineers.
  • Measure the risk.
  • Understand whether changes are minor or major.
  • Consider whether the existing dependency can still be used.
  • Consider launch delay if risk is too large.
  • Communicate carefully to stakeholders.
  • Explore demo-first or fallback options.

Key Feedback

Important misunderstanding:

  • The scenario says the external API is unstable.
  • It does not necessarily mean your team is updating a dependency version.

Focus first on:

  • Error rate
  • Latency
  • Downtime
  • Affected functionality
  • SLA
  • Fallback
  • Alternative provider

Polished Answer

First, I would validate the risk with the engineering team and collect concrete facts about the external API instability, such as its failure rate, latency, affected functionality, and how critical the dependency is to our launch.

Then I would assess the risk based on probability and impact. If the API is only affecting a non-critical flow and we have a safe workaround, I would work with the team on a mitigation plan, such as retry mechanisms, caching, a fallback flow, or temporarily disabling the affected feature.

However, if the unstable API is critical to the core user journey and there is no reliable fallback, I would treat it as a high launch risk.

I would communicate this to stakeholders early, not wait until the deadline. I would explain the issue in business terms: what is affected, how likely the risk is, what the potential impact is, and what mitigation options we have.

I would then present clear options. For example, we could proceed with the original launch if the risk is controlled, launch with reduced scope if the affected feature can be isolated, or delay the launch if reliability or user impact would be unacceptable.

My goal would be to avoid surprising stakeholders while making sure the final decision is based on quantified risk rather than optimism.

Useful Framework

Risk → Probability × Impact → Mitigation → Contingency → Owner → Communication

Q8

Critical-Path Delay

Interview Question

One backend task is on the project’s critical path, but the engineer says it will be delayed by three days because implementation is more complex than expected. What would you do to prevent the delay from affecting the overall project deadline?

Your Core Answer

  • Clarify what “complex” means.
  • Validate the reason for the delay.
  • Break the task into smaller components.
  • Use decomposition / modularization.
  • Start with easier sub-parts.

Key Feedback

Do not spend too much time proving whether the engineer’s technical complexity claim is valid.

Focus on:

  • Critical path
  • Remaining work
  • Parallelization
  • Resource reallocation
  • Downstream blockers
  • Mock/stub interfaces
  • Scope reduction
  • Escalation

Polished Answer

First, I would clarify with the backend engineer why the task is delayed and ask them to break down the remaining work, dependencies, and blockers.

Since the task is on the critical path, I would immediately assess whether the three-day delay can be absorbed elsewhere in the schedule or whether it will directly affect the final deadline.

If it affects the deadline, I would look for mitigation options. For example, I could split the task into smaller components, identify parts that can be worked on in parallel, assign another engineer to support the task, or temporarily deprioritize lower-impact work so that more capacity can be allocated to the critical-path item.

I would also check whether downstream teams are completely blocked by this backend task. If possible, we could provide a mock API, interface contract, or temporary stub so that frontend or QA work can continue while the actual implementation is being completed.

If the delay still cannot be recovered, I would communicate the impact to stakeholders early and present options, such as reducing scope or adjusting the delivery date, rather than waiting until the deadline is already missed.

My priority would be to protect the critical path, reduce idle time across the team, and make the impact visible as early as possible.

Q9

Agile / Scrum — Tickets Keep Carrying Over

Interview Question

Your team is using Scrum, but during several consecutive sprints, many tickets keep being carried over into the next sprint. What would you investigate, and what actions would you take to improve sprint predictability?

Your Core Answer

  • Define clear acceptance criteria.
  • Estimate effort.
  • Use person-days / man-days.
  • If work is too large, split it across multiple sprints.

Key Feedback

Look beyond ticket size.

Possible root causes:

  • Oversized tickets
  • Poor estimation
  • Unclear requirements
  • Hidden dependencies
  • Unplanned work
  • Blockers
  • Overcommitment
  • Capacity mismatch

Polished Answer

First, I would investigate the pattern behind the carry-over. I would check whether the tickets were too large, whether the requirements and acceptance criteria were clear before the sprint started, whether there were unexpected dependencies or blockers, and whether the team consistently overcommitted compared with its actual capacity.

Then I would improve sprint planning by making sure each ticket has clear acceptance criteria and a reasonable effort estimate before being committed to the sprint.

If a feature is too large to be completed within one sprint, I would split it into smaller deliverable stories instead of carrying the entire feature across multiple sprints.

I would also compare planned work with the team’s historical velocity or actual capacity, so we do not keep committing more work than the team can realistically finish.

During retrospectives, I would review the root causes of carried-over tickets and turn those findings into concrete actions for the next sprint.

The goal would be to improve predictability, not simply push the team to finish more work.

Q10

Project Status Reporting

Interview Question

Your manager asks for a project status update. The project is mostly on track, one milestone is at risk, and there are two unresolved blockers owned by other teams. How would you structure your status update?

Your Core Answer

  • Start with good news.
  • Mention that most of the project is on track.
  • Mention milestone risks and blockers.
  • Prepare solutions before escalating.
  • Explain risks carefully.
  • Avoid bringing a problem without a proposed solution.

Key Feedback

Do not hide or soften risk merely to keep management comfortable.

Management needs:

  • Accuracy
  • Concision
  • Decision-ready information

Avoid phrases like:

  • “a little bit of spice”
  • “so the manager will not be frustrated”

Polished Answer

I would structure the update in a concise and decision-oriented way.

First, I would give an overall project status, for example whether the project is green, yellow, or red, and briefly explain why.

Then I would summarize what is on track, followed by the milestone that is currently at risk. I would explain the expected impact if that risk materializes, including whether it affects the timeline, scope, or dependencies.

For the two blockers owned by other teams, I would clearly state the blocker, the owner, how long it has been open, and what escalation or support is needed.

I would also include the mitigation plan that we have already prepared, so I am not only reporting problems but also presenting possible actions.

Finally, if management needs to make a decision, I would make that explicit, for example: “We need approval to deprioritize Feature X,” or “We need escalation to Team Y by tomorrow to protect the milestone.”

My goal would be to make the update transparent, concise, and actionable.

Useful Structure

Overall Status → Progress → Risks → Blockers → Mitigation → Decision Needed

Q11

Failure / Lesson Learned

Interview Question

Tell me about a time when a project or task did not go as planned. What happened, what did you do, and what did you learn from it?

Your Core Answer

Example from SEVIMA:

  • Expected AI chat endpoint to use WebSocket / real-time streaming.
  • Backend engineer did not yet have enough experience with the implementation.
  • You simplified scope to a normal request-response API.
  • Real-time streaming was moved to a future sprint.
  • Engineer was given time to learn.
  • Lesson:

- Know the team’s competencies.

- Communicate before assigning difficult tasks.

- Trust and transparency are important.

Key Feedback

Frame the lesson around your planning assumption, not the engineer’s lack of skill.

Better:

“I realized that I had assumed the team was already comfortable with WebSocket-based streaming without validating that assumption during planning.”

Polished Answer

During my Project Management internship at SEVIMA, one feature did not go exactly as planned. I expected the AI chat endpoint to support real-time streaming using WebSocket, similar to the typing effect users see in modern AI applications.

However, during implementation, I realized that I had assumed the backend engineer was already comfortable with that approach without validating it during planning. Implementing it immediately would have increased delivery risk.

So instead of forcing the original scope, I proposed delivering a simpler request-response API first so the core chat functionality could still be completed within the sprint. We then moved the real-time streaming improvement back to the Product Backlog and planned to revisit it after the engineer had enough time to learn and prepare.

The main lesson for me was that technical planning should not only consider what the ideal architecture is, but also the actual capability, capacity, and readiness of the team.

Since then, before assigning technically demanding work, I try to validate the team’s familiarity with the technology, discuss implementation risks early, and make sure everyone is comfortable raising concerns before the sprint starts.

I also learned that trust and communication are critical. Engineers should feel safe being transparent about uncertainty, because hiding uncertainty can create much larger delivery problems later.
